# Review Desk

A keyboard-first, local workspace for your GitHub and GitLab code reviews. It shows what needs you, lets you review the change (including exactly what changed since your last review, across rebases and force pushes), and posts comments, replies and reviews through your own GitHub CLI or GitLab CLI login. Optional AI help runs through the Codex or Claude Code CLI on your machine. Everything runs on `127.0.0.1`; there is no hosted service and no GitHub App.

## Start

Requires Node.js 24, pnpm 10, and the GitHub CLI (`gh`) or the GitLab CLI (`glab`) logged in; either or both work. Codex, Claude Code and a Linear key are optional.

```bash
cd pr-review-dashboard
pnpm install --frozen-lockfile
pnpm build
pnpm start
```

Open **http://127.0.0.1:4317**. Keep the process running; it syncs in the background. In Chrome or Edge, use _Install Review Desk_ in the address bar to get a dock icon with a badge and desktop notifications.

`pnpm demo` runs the same app on **http://127.0.0.1:4319** against a fictional scenario (no GitHub, no AI quota, nothing posted anywhere). `pnpm dev` and `pnpm dev:demo` run Vite with hot reload (UI on 4317 / 4319, API on 4318 / 4320).

## What it does

**Inbox.** Pull requests that need you, grouped into follow-ups (new commits since your review, review re-requested, replies in your threads, @mentions, dismissed reviews) and first reviews. _Waiting on author_, _Caught up_ and _Snoozed_ hold the rest. `E` marks a PR done until something new happens; `S` snoozes it (presets, or type "fri 2pm"); new activity always brings a PR back. The URL holds the queue, filters and selected PR, so views are linkable and Back works.

**Adding PRs by hand.** The inbox tracks PRs that request your review, are assigned to you, that you reviewed, or that mention you. To review any other open PR, click _Add PR_ in the inbox header and paste its link or `owner/repo#123` (for GitLab, an MR link or `group/project!123`), paste it into the command palette (`⌘K`), or open its link and click _Add to review queue_ on the _Not tracked_ screen. It joins your first reviews like a review request, including automatic review when that is on, but without an "asked for your review" notification. It stays until it is merged or closed; _Remove from queue_ in the PR view drops it again, unless GitHub also lists you on it.

**Review workspace.** `Enter` opens the diff: a file tree with viewed state (synced with GitHub), one file at a time with syntax highlighting, unified or split, and review threads inline under their lines. When the branch moved after your review, it opens _Since your review_ automatically: an exact diff for new commits, or a file-by-file comparison of what you reviewed against what is there now after a rebase or force push. Select lines and press `C` to comment; comments stay as local drafts until you finish the review. `R` replies to a thread and `Shift+R` resolves it; both post immediately and say so. `⌘⇧↵` opens the Finish sheet: pick Comment, Approve or Request changes, add a summary, and submit. It warns when new commits arrived while you were reviewing, re-anchors your draft comments to the new code, and flags any that sit on changed lines. Approving resolves all open review threads before submitting the review.

**My PRs.** Your own open PRs grouped by whose move it is (needs you, waiting on reviewers, ready to merge, drafts), each with a checklist of what blocks it and the next step, including re-requesting a review in place. Waits longer than a day are flagged.

**Full review.** Open a PR in the dashboard and click _Run review_. The server downloads repository snapshots at the PR's merge base and exact head, and Codex inspects the complete change, surrounding code and relevant tests in read-only mode. The report stays on the PR with its findings and review coverage; running a review never posts to GitHub unless you turn on _Post findings to the PR_ (see below). Select the findings you want to include, click _Prepare GitHub review_, edit the summary and choose Comment, Approve or Request changes in the Finish sheet, then submit explicitly. Prepared reviews include the summary and selected findings in one review body without creating inline comments, with concise evidence of what was checked and why the code looks correct even when no changes are needed; detailed review coverage stays in the dashboard. Approve is selected by default when the report has no blocking findings, and you can change the verdict before submitting. Existing drafts are preserved, and an out-of-date report must be regenerated before preparing a review. Repository downloads are limited to 100 MB per compressed snapshot; symlinks, submodules and files beyond the extraction limit are unavailable and reported to Codex as coverage gaps. Codex does not execute repository code or tests.

**Automatic reviews.** Turn on _Review requested PRs automatically_ under Settings → Automation and a full review starts as soon as your review is requested: directly, through one of your teams, by assignment, or again after you already reviewed. Requests already waiting when you turn it on are not reviewed; requests that arrive while the server is stopped are picked up after the next sync. Draft PRs wait until they are ready for review, and a PR with a review already running or paused is left alone. When new commits arrive while an automatic review is running, it is stopped (its Codex process ends) and a fresh review of the latest commits starts once the PR has had no new commits for 5 minutes; each push during the wait starts it over, so a burst of pushes is reviewed once. This also applies to commits that only show up once the review has finished or failed (when GitHub cannot be asked right then, a later sync checks, counting only commits dated before the review finished; a new request on the PR waits for that check), to reviews saved by a server restart, and to reviews that kept running while automatic review was turned off and on again. Reviews you started or paused yourself are never stopped, a review you start during the wait takes the place of the restart, even if you stop it, and a new review request during the wait waits with it. Turning automatic review off drops pending restarts. Inbox rows show _AI review restarting_ and the full review panel says when the fresh review starts. Automatic reviews use your ChatGPT plan like any other full review and wait while the plan's limit is reached. Inbox rows show whether a full review is running, ready, out of date or failed, and an _Automatic AI reviews ready_ notification tells you when one finishes. Automatic review stops at the report unless _Post findings to the PR_ is on. When posting is off, select findings, prepare the GitHub review and submit it yourself.

**Posting findings.** Turn on _Post findings to the PR_ under Settings → Automation and every full review that finishes, automatic or started by you, is posted from your account as one conversation comment with its summary and findings. Turn on _Approve when there are no blocking findings_ as well and such a review approves the PR instead, with the summary and findings in the review body, but only when it read every changed file: Review Desk lists the files the reviewed commits change (by comparing the two commits on GitHub, up to 300 files, or from GitLab's stored diff version) and checks that each one is in the downloaded snapshots. A review that could not read every file, or on a draft or your own PR, comments instead and says why. _Resolve threads before approving_ resolves the open review threads the review read; threads opened later are never touched. Settings saved before these switches existed keep approving and resolving as posting did then; turned on now, posting starts as comments only. The decision is saved together with the finished review, so a crash cannot lose it, and the full review panel shows whether it approved, commented and why, or was not posted and why, with a link to GitHub. Posts include the reviewed commit and never create inline comments. Each post goes through Activity with account checks, retries and recovery; lost responses are confirmed from GitHub before another attempt, except a thread resolution, which waits for you in Activity because a resolved thread does not say who resolved it, and on GitLab an approval, for the same reason. A review is posted once. Right before each step goes out, Review Desk checks that posting, and approving or resolving where the step does that, are still turned on, that the PR still shows the reviewed diff (same commit, target branch and merge base, with the target branch still on the commit that merge base was found from) and that its discussion did not change: a new or edited comment, thread or review of yours, another reviewer's new verdict, another AI post, or a reopened thread stops it. Before anything was sent, the post is then skipped with the reason; after, the rest waits in Activity. Failed or stopped reviews, reviews already finished when you turn it on, reviews whose PR or discussion changed while they ran, and reviews that finish after you switch accounts are not posted; a post already waiting goes out once you switch back. Approvals queued by an earlier version wait in Activity for you. When the finished review cannot be saved, it shows as failed: _Resume_ returns its answer when Codex kept a checkpoint, otherwise run it again. Your own posted comment does not mark the review out of date. Review Desk reads other reviewers' verdicts but not the text of their reviews, and only the latest 50 conversation comments, so an edit to another reviewer's review text or to an older comment goes unnoticed. On GitLab a merge request is read in several requests, the target branch last, so a change made while that last request is answered is seen by the next check rather than this one. GitLab approvals take no text, so there the approval and its summary are two steps in Activity, each confirmed on its own: a summary GitLab refuses is sent again without approving twice, and is checked again first like the approval was. The summary goes only with the approval this post gave, recorded as it is given: withdrawn or replaced, the summary waits for you. A withdrawal and approval again by hand within the single read that records it cannot be told apart. Automatic GitLab approvals queued by an earlier version are not sent by this one: one that sent both at once and was refused is marked done when both are on the merge request, and any other waits in Activity for you to check.

**AI assist.** `B` writes a brief (summary, risk, files to read closely, questions); on PRs you already reviewed it also judges whether each of your threads was addressed. `Shift+B` in the workspace suggests review comments anchored to real lines; you accept them one at a time into your draft, and nothing is ever posted for you. The Finish sheet can draft your review summary using the diff, pending comments and any completed full review of the current head. Codex is the default; pick Claude Code per run or per task in Settings, along with how much effort each task uses. Full reviews always use Codex, with high effort by default. Up to two AI tasks, including two full reviews, can run in parallel; additional tasks wait in order until a slot is free. Results are cached per commit and marked out of date when the branch moves.

**Saved reviews and summaries.** Preparation and summary generation continue when you navigate away. Return to see progress, reopen the prepared review with your edits, use a saved generated summary, or generate a new one. Preparing another run or changing the selected findings replaces the previously prepared summary and findings while keeping independent comments and surrounding summary text. Edited prepared content requires confirmation; a copy of the current draft stays available under _Saved drafts before replacement_ in the Finish sheet. Results show their generation time, commit and freshness. New commits, base changes or review discussion make a review out of date; summaries also need regeneration after verdict or draft comment changes, or a newer full review. Reuse checks live GitHub before applying a saved result. Failed or stopped replacements keep the previous completed result available, and summaries replace your text only when you explicitly choose to use them.

**Pause and recovery.** Codex reviews and summaries save their thread and exact inputs locally. _Pause_ preserves the investigation; _Resume_ continues the same run and thread after checking that the PR and task inputs are still current. Server shutdowns save running and queued Codex tasks, and startup resumes them automatically after GitHub reconnects, within the same two-task limit. User-paused tasks stay paused. A missing workspace is rebuilt at the saved commits; a completed answer already in the thread is recovered without another model turn. Changed PRs or review instructions require a new generation. _Stop_ discards the checkpoint. Paused and recoverable failed runs retain their workspace; completed and discarded runs remove it. Claude and older runs created without checkpoints still require a new run after interruption. Recovery restores persisted conversation history; work interrupted before it was saved can be repeated.

**Linear.** Ticket ids in branches (`fix/APP-123/...`), titles (`fix(APP-123): ...`) and Linear links show as chips, and the PR view shows each issue's state, priority and owner.

**Notifications and badge.** New review requests, pushes after your review, replies, mentions, approvals or failing checks on your own PRs, and finished automatic reviews. You get a toast while you are looking at the app and a desktop notification otherwise, with per-kind toggles and quiet hours. Optional native macOS notifications cover the time no window is open. The badge shows how many PRs need you.

**Insights.** Median and 90th-percentile time to review, reviews per day or week, how many waited past your target, your queue over time, your verdict mix, per-repository numbers, and how long your own PRs wait for a first review. History is read from GitHub for the last 90 days, then recorded as you work.

## Setup for the optional parts

**AI.** Install and log in to the Codex CLI (`codex`) and/or Claude Code (`claude`). Settings shows which are found. Agents run headless in a private scratch folder with no GitHub credentials; full reviews include repository snapshots that are removed when the run finishes or is stopped. Codex runs through `codex app-server`, the way Codex's IDE extension does, on your ChatGPT sign-in, so it uses your ChatGPT plan. A Codex signed in with an API key is refused. Runs are paused while the plan's limit is used up, and a run that reaches the limit midway is stopped, so the dashboard never falls back to credits; Settings → AI agents shows the plan, its usage and when it resets. A run also says so if your Codex credit balance fell while it ran. Codex runs read-only, with its connectors, plugins, browser, web search, notify hook and your MCP servers turned off, at standard speed even if your Codex config asks for Fast mode. Each task can pick a model your account offers (a model it stops offering falls back to the default). The default is the first of GPT-6.1-Sol, GPT-6-Astra, GPT-5.6-Sol and GPT-5.6-Terra your account offers to Review Desk, else your account's own default, never the model pinned in your Codex config. OpenAI offers GPT-6.1-Sol only to Codex CLI 0.159.0 and later, so run `codex update` if Settings does not list it. Claude runs with no tools, no MCP servers and your user settings only. PR content is sent to the agent's own service under your subscription.

**Linear.** In Settings → Linear, click _Connect Linear_ and approve read-only access in Linear. This signs in through Linear's MCP server (OAuth with PKCE), so it works in workspaces where personal API keys are turned off. The sign-in is kept in your macOS Keychain (item `review-desk.linear-oauth`), refreshes itself, and _Disconnect_ removes it. Where personal API keys are allowed (Linear Settings → Security & access → Personal API keys) you can use one instead; store it in the Keychain from a terminal so the key never passes through the app:

```bash
security add-generic-password -U -s review-desk.linear -a api-key -w
```

**Notifications.** In Settings → Notifications, click _Allow notifications_. Native macOS notifications for when no window is open are opt-in; clicking one opens Script Editor rather than the PR.

## GitHub account and safety

The server calls `gh api` with your GitHub CLI login. No token is stored or sent to the browser; when you pick an account in the app (below), the server reads that account's token with `gh auth token --user` and passes it only to the `gh` commands it runs, keeping it in memory for at most a minute. Every write is an explicit action in the UI and states who it posts as, except finished AI reviews when you turn on _Post findings to the PR_. GitHub actions are saved in a durable SQLite outbox before the editor closes. Open **Activity** in the status bar or command palette to inspect progress, saved content, GitHub links, and recovery options. Queued reviews are read-only across tabs; other PRs remain editable. Inbox reviews advance after queue acceptance, while standalone PR pages stay open.

The worker rechecks the live account before each mutation, paces writes, honors rate-limit cooldowns, and validates the reviewed commit before submission. Confirmed steps are checkpointed so recovery resumes the remaining work. If a request may have reached GitHub without a response, Activity checks what it can verify and leaves ambiguous results **Unconfirmed** instead of automatically repeating them. Cancellation is available until sending starts. Cleanup of a partial pending review requires confirmation and saves its GitHub content before restoring the local draft.

Actions continue when the browser closes while the local server remains running. After a server restart, unsent actions resume automatically; interrupted mutations are checked first. Replies attached to an existing GitHub pending review are labeled as pending rather than posted. Viewed-file updates sync quietly and report failures in Activity.

The app binds to `127.0.0.1` only, rejects unexpected hosts and origins, and requires a per-launch session token on every write. Pages cannot be framed, user Markdown renders without raw HTML or remote images, and errors are scrubbed of tokens and keys.

**Several GitHub accounts.** Sign in to each github.com account with `gh auth login`, then switch from the account menu at the bottom of the sidebar, Settings → GitHub, or the command palette. Review Desk works as one account at a time and keeps each account's queue, notes, drafts, actions, AI results and history apart. Switching never runs `gh auth switch`, so terminals and git keep the GitHub CLI's own active account, and your choice is kept across restarts; until you pick one, Review Desk follows the CLI's active account. An action already being sent finishes first. Actions still queued for the previous account stay saved and send when you switch back; the menu shows how many are waiting. AI reviews and history imports already running finish as the account that started them. Notifications, automatic reviews and the badge cover the account in use; requests that arrive for another account are picked up after you switch back.

## GitLab

Review Desk works with GitLab.com and self-managed GitLab through the GitLab CLI. Sign in to each instance with `glab auth login --hostname git.example.com` (or plain `glab auth login` for GitLab.com), then pick the account from the account menu, Settings → GitHub & GitLab, or the command palette. The GitLab CLI keeps one account per host, so each signed-in host is one account, shown as `username@host`. It keeps its own queue, notes, drafts, actions, AI results and history, separate from a GitHub account with the same username. When the GitHub CLI has no github.com sign-in at all (or is not installed), Review Desk starts with the first signed-in GitLab account.

Every request runs `glab api --hostname <host>` from a private empty directory, so glab's settings for that host apply and no repository's local glab configuration can redirect it; tokens, hosts and API overrides from the environment (`GITLAB_TOKEN`, `GITLAB_API_HOST`, `GLAB_API_PROTOCOL` and the like) are ignored, as GitHub tokens from the environment are. Every write first checks that glab is still signed in as the account in use, and text Review Desk posts on its own, such as an automatic AI review, never runs GitLab quick actions. That covers custom ports (`git.example.com:8443`), `http` instances (`api_protocol`), a separate API host (`api_host`), private certificate authorities (`ca_cert`) and client certificates. A GitLab served under a path such as `https://example.com/gitlab` works when glab's API endpoint includes that path; pasted links keep it and Review Desk removes it. Review Desk never reads the GitLab token: glab sends it.

Merge requests appear wherever PRs do. Review requests, assignments, your own MRs and mentions (from your GitLab to-do items) fill the inbox and My PRs. GitLab keeps reviewers listed after they review, so a reviewer counts as requested until they comment, approve or request changes after being asked, and asking them again brings it back. Comments you add while reviewing are GitLab draft notes, so they are your pending review in GitLab too; finishing the review publishes them together with the summary and any drafts you started in GitLab. Comments and the approval stay on the commit the review started on: approving sends that commit, so GitLab refuses the approval if new commits arrived. Approving still resolves open threads first. Your reviews are read from your comments on code, approvals and change requests, and from reviews submitted here; activity within a minute counts as one review, and a comment in the conversation alone is not a review, as on GitHub.

Some things differ from GitHub. Requesting changes needs GitLab 19.2 or later, where publishing a review can set your reviewer state; on older instances the Finish sheet offers Comment and Approve, and you say what needs to change in the review. Review Desk reads the instance's version to decide. Replies post at once rather than joining your pending review. GitLab has no API for viewed files, so files you mark viewed are kept by Review Desk and show as changed when their diff changes. GitLab asks people, not teams, for reviews, and has no search for MRs you commented on without being a reviewer, so those appear only when you are mentioned or add them by hand. CI shows the head pipeline's jobs. Change detection makes one request per project and also polls the pipeline of MRs whose CI is still running, because pipeline results do not change an MR's update time. Full reviews download the repository archive at the reviewed commits with glab; AI agents get no GitLab token and an empty glab configuration.

## Data, backup and recovery

Everything lives in `.data/` (SQLite: cached PRs, notes, drafts, queued GitHub actions and receipts, triage, AI results, history). Schema upgrades back up the previous database first (`.data/backup-before-<migration>.sqlite`, or `.data/backup-v<N>.sqlite` for databases from before Drizzle). To back up, stop the app and copy `.data/`. To start fresh, stop the app and rename `.data/`. Notes and drafts are stored locally but not encrypted, so protect the folder like other work data.

One Review Desk process uses a data folder at a time. A second `pnpm start` or `pnpm dev` on the same folder exits with "Review Desk is already running" before it opens the database, so it never touches the running one's queued actions or AI runs; to run another instance, give it its own `REVIEW_DESK_DATA_DIR` and `REVIEW_DESK_PORT` (`pnpm dev` always uses Vite on 4317, so run a second instance with `pnpm start`). The hold ends when the process exits, even after a crash. Stopping the app (Ctrl-C) stops new work first, lets the action being sent and running AI reviews reach a safe point for up to 20 seconds, then exits; a second Ctrl-C exits at once, and anything interrupted is checked on the next start.

Syncing is incremental: a cheap fingerprint per PR decides when a full refresh is needed, with a full check every 30 minutes and on opening a PR. Search failures never drop a PR, and a PR leaves the list only once GitHub confirms it was closed or merged, or you remove a PR you added by hand.

The server keeps a log in `.data/logs/review-desk.log` (only you can read it). It holds measurements and nothing you wrote: each line is a JSON record of a fixed kind with fixed fields. The fields are timings, counts, HTTP statuses, error codes, a request's route as the server declares it (`/api/pulls/:id`) and what a `gh` or `glab` request did (`Snapshot`, `pulls.files`, `mr.discussions`). The log never contains PR text, reviews, comments, diffs, file or branch names, URLs, logins or tokens. It records:

- each sync, by phase and count;
- slow requests, and every server error;
- slow `gh` and `glab` calls;
- repository downloads for full reviews;
- event-loop delay that would make the app feel slow.

Past about 10 MB the file is rotated, keeping five older ones (`review-desk.log.1` to `.5`). A disk that stalls or fills loses log records, never the app. `REVIEW_DESK_LOG_LEVEL=debug` also records every request, every `gh` or `glab` call and the event-loop delay every 10 seconds. That is enough to check a real session against the performance targets with `pnpm --filter @review-desk/server log:summary .data/logs/review-desk.log`. It reports each route's p50 and p95 against a 100 ms p95, and the worst 10-second window's event-loop p99 against 50 ms. Windows with too few samples are left out.

## Development

The repository is a pnpm workspace with one lockfile. `apps/web` (`@review-desk/web`) contains the React, TypeScript and Vite frontend (TanStack Router and Query, Tailwind CSS, Radix primitives, `@pierre/diffs`). `apps/server` (`@review-desk/server`) contains Fastify, Drizzle ORM over Node's built-in SQLite, GitHub, sync, reviews, AI, Linear, notifications and insights. `packages/shared` (`@review-desk/shared`) contains browser-safe contracts and pure rules for attention, author blockers, diffs, tickets and insights.

Each workspace has its own dependencies, TypeScript configuration and unit or component tests under `tests/`. End-to-end tests, common test fixtures and the GitHub GraphQL schema stay in the root `tests/` directory. The root commands run the complete app and test suite:

```bash
pnpm test          # unit and component tests (Vitest)
pnpm e2e           # builds, then Playwright against demo mode in light and dark, with axe scans and visual baselines
pnpm typecheck
pnpm format:check
pnpm db:check      # the migration history is consistent (Drizzle Kit's check)
```

GitHub Actions runs these on every pull request and on `main` (`.github/workflows/ci.yml`). Format, types, unit tests and the migration history run in one job. End-to-end tests run on Linux with `--ignore-snapshots`, because the visual baselines are macOS renderings. A separate macOS job compares the screenshots too; it reports a difference without failing the change, since a hosted runner's fonts can render slightly differently from the Mac the baselines were recorded on.

Within a workspace, `@/` points to that workspace's `src/` directory. For example, the web app imports `@/ui/button`, and the server imports `@/db/store.js`. Node ESM imports in the server and shared package retain their `.js` extension; their builds rewrite aliases to relative JavaScript imports so production runs with plain Node. Imports between workspaces use package names such as `@review-desk/shared/ai`, declared with `workspace:*` dependencies. Tests use `@test/fixtures` for the common root fixtures. Vite and Vitest resolve aliases from the importing workspace; TypeScript and tsx use that workspace's configuration.

Animation uses the `motion` library through one layer in `apps/web/src/ui/motion/`. Features compose its primitives (`Reveal`, `FadeSwap`, `SmoothHeight`, `Enter`, `ListPresence` and `ListItem`, `ActiveIndicator`, `StaggerItem`) and the overlay primitives in `apps/web/src/ui/` (`Modal`, `Drawer`, `Menu`, `Popover`, `Tooltip`). They never import `motion/react` or set timings themselves, and a new kind of motion becomes a new primitive. Timing comes from `ui/motion/tokens.ts`, which `app.css` mirrors as `--motion-*` custom properties for CSS transitions. Panes and pages animate in only, so keyboard navigation never waits for an exit. A region that loads shows a skeleton from `ui/skeleton.tsx`, which appears only when the load takes longer than a short delay, and a failure shows `ErrorState` with a way to try again. Each state eases into the next, and a card that changes shape eases its height with it. Content inside the diff virtualizer only fades, so its row measurements stay correct. When the OS asks for reduced motion, every animation is instant. `apps/web/tests/architecture.test.ts` enforces these boundaries and keeps the CSS tokens equal to the TypeScript ones. Component tests skip animations through `apps/web/tests/setup.ts`, so a test waits for a removal with `waitFor` or `findBy` and never times it.

`pnpm dev` builds shared code, then watches the shared package, API and web app together. `pnpm build` typechecks all workspaces and tests before building their production outputs. `pnpm start` serves `apps/web/dist` from the built server at `apps/server/dist/index.js`. Existing `.data/` and `.data-demo/` directories remain at the repository root, including when commands run from a workspace directory.

To run a package's tests alone, use `pnpm --filter @review-desk/web test`, `pnpm --filter @review-desk/server test` or `pnpm --filter @review-desk/shared test`. After shared code has been built, `pnpm --filter <package> typecheck` checks that workspace and its tests.

To change the database schema, edit `apps/server/src/db/schema.ts`, run `pnpm db:generate --name <change>` and commit the new folder under `apps/server/drizzle/`. The app applies pending migrations on start. Never edit a migration that has already been released; generate a new one instead.

`pnpm bench` measures the server on synthetic workloads: 500 and 1,000 PRs across 20 repositories, one PR with 3,000 changed files and 300 threads, and one rebased since your review with 400 changed files. All of it is in memory behind the demo forge. It times:

- cold and warm syncs (one changed PR);
- `/api/pulls` on a populated 1,000-PR account, idle and while a background sync of 100 changed PRs runs (samples count only while it runs);
- the inbox and My PRs derivations;
- the large PR's full diff, cold;
- the rebased interdiff, cold, with the longest event-loop stall around each build;
- the large PR's fingerprints.

It prints a table with each gate's verdict (route p95 under 100 ms, stall under 50 ms) and writes `bench-results.json`. Run it on a representative machine before and after a change that could affect speed; `BENCH_SMOKE=1` runs a small version, as `pnpm test` does. `pnpm bench:forge` compares matched GitHub requests through `gh api` and through direct HTTPS with the same sign-in, to estimate what the CLI itself costs. It reads the token from `gh auth token` for those requests only, never stores or prints it, and is never run by CI.

Every GraphQL document is validated against GitHub's published schema (`tests/schema/github.graphql`). Demo mode (`apps/server/src/demo/`) models commit graphs, force pushes, GitHub writes with a write log and failure injection, Linear issues, AI answers and review history, so end-to-end tests never touch GitHub or spend AI quota.
